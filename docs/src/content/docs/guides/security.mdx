Tutti has multiple layers of security built in. This guide covers each one and how to configure them.

## Permission system

Voices declare `required_permissions`. Agents must explicitly grant them.

```ts
{
  coder: {
    voices: [new FilesystemVoice()],  // requires: ["filesystem"]
    permissions: ["filesystem"],       // must be granted explicitly
  },
}
```

If permissions are missing, the runtime throws before executing anything:

```
Voice filesystem requires permissions not granted: filesystem

Grant them in your score file:
  permissions: ['filesystem']
```

The four permission types:

| Permission | Grants access to |
| ---------- | ---------------- |
| `filesystem` | Local file read/write |
| `network` | HTTP requests, API calls |
| `shell` | Shell command execution |
| `browser` | Browser automation |

:::tip
The runtime logs a warning for agents with `filesystem` or `shell` permissions, since these are the most powerful.
:::

## Secret redaction

The `SecretsManager` automatically redacts known API key patterns from:

- Event bus payloads (so logging doesn't leak keys)
- Tool error messages (so the LLM doesn't see raw keys)

Detected patterns: Anthropic keys (`sk-ant-*`), OpenAI keys (`sk-*`), GitHub tokens (`ghp_*`), Google API keys (`AIza*`), Bearer tokens.

```ts
SecretsManager.redact("Key is sk-ant-api03-abcdef...")
// → "Key is [REDACTED]"
```

## Path traversal protection

The filesystem voice blocks access to system paths:

- `/etc/passwd`, `/etc/shadow`, `/etc/hosts`
- `~/.ssh`, `~/.aws`
- `/proc`, `/sys`, `/dev`

It also enforces a maximum file size on reads (default 10MB).

```
> Read /etc/passwd
  Error: Access to system path not allowed: /etc/passwd
```

## URL sanitization

The Playwright voice blocks dangerous URL schemes:

- `file:`, `javascript:`, `data:` — local file access, script injection
- Private network ranges (`10.x`, `172.16-31.x`, `192.168.x`) — SSRF prevention

## Prompt injection defense

Tool results are scanned by `PromptGuard` for common injection patterns:

- "Ignore all previous instructions"
- "You are now..."
- "New instructions:"
- "System prompt:"
- "Forget everything"
- "Your new role/purpose/goal"

When a pattern is detected:
1. The content is wrapped with boundary markers and a data-only warning
2. A `security:injection_detected` event is emitted

```ts
tutti.events.on("security:injection_detected", (e) => {
  console.warn(`Injection detected in ${e.tool_name}:`, e.patterns);
});
```

:::note
The PromptGuard does not block content — it wraps it with markers that instruct the LLM to treat it as data, not instructions. The original content is preserved.
:::

## Budgets

Set per-agent budgets to prevent runaway costs:

```ts
{
  assistant: {
    budget: {
      max_tokens: 50_000,             // soft cap on total tokens (event + return partial)
      max_cost_usd: 1.00,             // hard per-run USD cap (throws BudgetExceededError)
      max_cost_usd_per_day: 50.00,    // hard daily cap, aggregated across all runs
      max_cost_usd_per_month: 500.00, // hard monthly cap
      warn_at_percent: 80,             // emit warning at 80% per scope (default)
    },
  },
}
```

Two enforcement modes:

| Limit | Mode | Behaviour on breach |
| ----- | ---- | ------------------- |
| `max_tokens` | Soft | Emits `budget:exceeded`, returns the partial run result. |
| `max_cost_usd` | Hard | Throws `BudgetExceededError` with `scope: 'run'`. |
| `max_cost_usd_per_day` | Hard | Throws with `scope: 'day'`. Requires a `RunCostStore` on the runtime. |
| `max_cost_usd_per_month` | Hard | Throws with `scope: 'month'`. Requires a `RunCostStore` on the runtime. |

Daily/monthly caps query a `RunCostStore` at run start and add this run's accumulating cost to the snapshot. Use `PostgresRunCostStore` in any deployment with more than one worker so every process shares the same total — `InMemoryRunCostStore` is for dev and tests.

```ts
import { TuttiRuntime, PostgresRunCostStore } from "@tuttiai/core";

const runtime = new TuttiRuntime(score, {
  runCostStore: new PostgresRunCostStore({
    connection_string: process.env.DATABASE_URL!,
  }),
});
```

Events:
- `budget:warning` — emitted when usage crosses `warn_at_percent`. Carries `scope: 'run' | 'day' | 'month'` and numeric `limit`.
- `budget:exceeded` — emitted on breach. Same `scope` / `limit` fields. The hard-throw caps additionally throw `BudgetExceededError` (catch it on `runtime.run()`).

```ts
import { BudgetExceededError } from "@tuttiai/core";

try {
  await runtime.run("assistant", "do the thing");
} catch (err) {
  if (err instanceof BudgetExceededError) {
    console.log(`Stopped: ${err.scope} budget hit ($${err.current} of $${err.limit})`);
  } else {
    throw err;
  }
}
```

## Tool rate limiting

Two rate limits protect against runaway tool execution:

| Config | Default | Description |
| ------ | ------- | ----------- |
| `max_tool_calls` | 20 | Max tool calls per `run()` |
| `tool_timeout_ms` | 30000 | Per-tool timeout in milliseconds |

```ts
{
  assistant: {
    max_tool_calls: 10,
    tool_timeout_ms: 15_000,
  },
}
```

If a tool exceeds the timeout, the error is returned as a `tool_result` (not thrown), so the LLM can recover gracefully.

## Guardrails (`beforeRun` / `afterRun`)

Wrap agent inputs and outputs with policy hooks. Each hook runs synchronously around the agent loop and can block, rewrite, or annotate the run.

```ts
import { defineScore, profanityFilter, piiDetector, topicBlocker } from "@tuttiai/core";

export default defineScore({
  provider: new AnthropicProvider(),
  agents: {
    assistant: {
      name: "Assistant",
      system_prompt: "You are a customer-support agent.",
      voices: [],
      // Input guardrails — run before the first LLM call
      beforeRun: [
        profanityFilter({ on_match: "block" }),
        piiDetector({ on_match: "redact" }),
      ],
      // Output guardrails — run after the agent's final response
      afterRun: [
        topicBlocker({ topics: ["legal advice", "medical diagnosis"] }),
      ],
    },
  },
});
```

Each factory returns a `GuardrailHook`. Three built-in factories ship with `@tuttiai/core`:

| Factory | Purpose | Common config |
| ------- | ------- | ------------- |
| `profanityFilter(opts)` | Block / warn on profane input or output | `{ on_match: "block" \| "warn" \| "redact" }` |
| `piiDetector(opts)` | Detect / redact emails, phone numbers, SSNs, credit cards | `{ on_match, patterns? }` |
| `topicBlocker(opts)` | Refuse to answer prompts about listed topics | `{ topics: string[], on_match }` |

You can also write your own by implementing the `GuardrailHook` contract — any `(context) => Promise<GuardrailResult>` function with `action: "allow" | "block" | "rewrite"`. See [Guardrails](/guides/guardrails) for the full API.

## Approval gates (HITL)

Tools marked `destructive: true` wait for a person's approval by default. `requireApproval` widens or narrows that:

```ts
{
  assistant: {
    // Glob patterns on tool names; destructive tools stay gated too.
    requireApproval: ["send_*", "delete_*"],
    // Or "all" to gate every call, or false to gate nothing.
  },
}
```

When the agent attempts a gated tool call, the runtime writes an interrupt to the configured `InterruptStore`, emits `interrupt:requested`, and pauses the run. Review and resolve via the [`tutti-ai interrupts`](/cli/reference#tutti-ai-interrupts) TUI, the `/interrupts/*` HTTP endpoints, or the Studio UI. A client reading `POST /run/stream` receives an `approval_requested` frame carrying the `interrupt_id`, and the same stream continues once the call is approved.

Give the runtime a `checkpointStore` as well as an `interruptStore` and a turn that stops at the gate is saved as a pause checkpoint, rewritten as the turn's other calls finish. Resolving the approval when no run in the process is waiting on it (the process was restarted, or the stream's client went away) resumes the run from that checkpoint in the background:

- an approved call runs once, and a denial ends the run with `InterruptDeniedError` carrying the recorded reason;
- calls that had already finished are not run again, and a call the restart cut off gets an error result saying so instead of running twice;
- the resumed run goes through `TuttiRuntime.run`, so voice permissions are checked again, and its answer lands in the session rather than on the original stream;
- a second resolve of the same approval changes nothing, and two at once resume the run only once.

With stores that outlive the process (anything but `MemoryInterruptStore` and `MemoryCheckpointStore`), a run aborted while it waits leaves its approval pending instead of denying it with "run aborted". On the memory stores it is still denied, as nothing could resume it.

### Approvals across a restart in the server image

Pending approvals survive a restart of the server image when `TUTTI_PG_URL` is set (Postgres interrupt and checkpoint tables) or when `TUTTI_STATE_DIR` points to a writable directory (files under `<dir>/interrupts/` and `<dir>/checkpoints/`). Otherwise they are kept in memory, lost on restart, and a warning is logged at start: "pending approvals will not survive a restart; set TUTTI_STATE_DIR or configure Postgres". The started log line names the store in use as `durability: postgres|file|memory`.

- Stored approvals keep the tool's arguments in plain text under `<TUTTI_STATE_DIR>/interrupts/` (file mode 0600, directory 0700) or in the Postgres interrupts table. Protect that volume or database the way you protect sessions.
- A second resolve of the same approval is refused with 409 `already_resolved` and has no side effect: the run is not resumed twice and no tool runs twice.
- A resumed run calls PermissionGuard again, through `TuttiRuntime.run`.
- A record that cannot be read answers 500 `interrupt_record_corrupt` naming only its id, and is left out of `GET /interrupts/pending`; the other approvals keep working.

:::tip[Routing impact]
When the [smart router](./smart-routing) is enabled, agents with destructive tools loaded automatically bias toward larger, safer models. The cost of an LLM mistake on a destructive call (a posted tweet, a voided invoice, a deleted message) is far higher than the cost of using a smarter model for that turn — `SmartProvider` factors this into every routing decision.
:::

## Score validation

Score files are Zod-validated when loaded. Common mistakes are caught early:

- Missing `provider`
- Agent with empty `name` or `system_prompt`
- Negative `max_turns` or `max_tool_calls`
- Delegates referencing agents that don't exist
- Invalid permission values

Run `npx tutti-ai check` to validate without running.

## Claude Code provider environment

`ClaudeCodeProvider` starts the Claude Code CLI as a child process. The child does not inherit the server's environment. It gets only these variables, by exact name and only when they are set, read through `SecretsManager`:

| Group | Variables |
|---|---|
| System | `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `TMPDIR`, `TMP`, `TEMP`, `TERM` |
| Locale | `LANG`, `LANGUAGE`, `TZ`, `LC_ALL`, `LC_CTYPE`, `LC_MESSAGES`, `LC_NUMERIC`, `LC_TIME`, `LC_COLLATE`, `LC_MONETARY` |
| Network and TLS | `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`, `http_proxy`, `https_proxy`, `no_proxy`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR` |
| CLI login and config | `CLAUDE_CONFIG_DIR`, `XDG_CONFIG_HOME`, `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL` |

When `config_dir` is set, `CLAUDE_CONFIG_DIR` is set to it on top of the list.

Everything else stays behind, including `TUTTI_PG_URL`, `TUTTI_VOICES` and every other `TUTTI_*` variable, other providers' keys, `GITHUB_TOKEN`, `NODE_OPTIONS` (its `--require` can inject code), `NODE_ENV`, and the cloud credentials `AWS_*`, `GOOGLE_APPLICATION_CREDENTIALS`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX` and `ANTHROPIC_VERTEX_PROJECT_ID`. There is no wildcard: `LC_PAPER` or `CLAUDE_CODE_MAX_OUTPUT_TOKENS` is not passed either. MCP servers the CLI starts inherit from the CLI, so they see only the list too.

The CLI runs with no built-in tools (`--tools ""`), so this is defence in depth: a prompt injection that one day reaches a shell tool in the CLI still cannot print the server's database URL or voice tokens.

**Passing a variable through.** To give the CLI a variable that is not on the list, such as the Bedrock settings, supply your own `runner`. It receives each invocation, including `invocation.env` (the `config_dir` value, when set), and decides the child's environment itself:

```ts
import { spawn } from "node:child_process";
import { ClaudeCodeProvider, type ClaudeCodeRunner } from "@tuttiai/core";

const runner: ClaudeCodeRunner = (invocation) =>
  new Promise((resolve) => {
    const child = spawn(invocation.command, invocation.args, {
      cwd: invocation.cwd,
      env: {
        PATH: process.env.PATH ?? "",
        HOME: process.env.HOME ?? "",
        ...invocation.env,
        CLAUDE_CODE_USE_BEDROCK: "1",
        AWS_REGION: "eu-west-1",
      },
    });
    let stdout = "";
    let stderr = "";
    child.stdout.on("data", (chunk: Buffer) => (stdout += chunk.toString()));
    child.stderr.on("data", (chunk: Buffer) => (stderr += chunk.toString()));
    child.on("error", (spawn_error) => resolve({ exit_code: null, stdout, stderr, spawn_error, timed_out: false }));
    child.on("close", (exit_code) => resolve({ exit_code, stdout, stderr, timed_out: false }));
    child.stdin.end(invocation.stdin);
  });

const provider = new ClaudeCodeProvider({ runner });
```

This sketch leaves out `timeout_ms` and `signal`, which the built-in runner honours; add them if you rely on either.

**What is still exposed.** The CLI needs its login, so `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN`, and any password in a proxy URL, still reach the child and can be read by anything it runs. Use a key or token issued for this purpose only. The child also runs as the server's own user, so this is not isolation.

**Windows.** Names are matched case-sensitively, so Windows variables such as `Path`, `SystemRoot` and `PATHEXT` are not passed. Run the CLI on Linux or macOS, or pass them through your own `runner`.

## Best practices

1. **Least privilege** — only grant the permissions each agent actually needs
2. **Set budgets** — always set `max_tokens` or `max_cost_usd` in production
3. **Monitor events** — subscribe to `security:injection_detected` and `budget:warning`
4. **Keep .env out of git** — the `.gitignore` template already excludes it
5. **Pin dependencies** — all Tutti packages pin exact dependency versions
