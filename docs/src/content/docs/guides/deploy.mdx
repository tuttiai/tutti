Tutti ships a deploy bundler, `@tuttiai/deploy`, and a CLI front-end on it. One command takes a score from `tutti-ai run` to a running service on your platform of choice. The bundle includes whatever the target needs (a Dockerfile + `docker-compose.yml` for the container targets, a `modal_app.py` for Modal, a devcontainer + snapshot config for Daytona), generated from a `DeployConfig` block on your agent.

v0.26 adds two serverless targets, **Modal** (scale-to-zero functions) and **Daytona** (always-warm dev sandboxes), alongside the original Docker / Railway / Fly. Cloudflare Workers is recognised as a `DeployTarget` value but no bundler ships yet; the CLI errors loudly rather than half-deploying.

## Prerequisites

- A Tutti score that runs locally with `tutti-ai run` or `tutti-ai serve`
- The platform CLI installed:
  - Docker: `docker compose` (built in)
  - Railway: `npm i -g @railway/cli && railway login`
  - Fly: `curl -L https://fly.io/install.sh | sh && fly auth login`
  - Modal: `pip install modal && modal token new`
  - Daytona: `brew install daytonaio/cli/daytona && daytona auth login`

## Step 1: Add a `deploy` block to one agent

Pick the agent you want to ship and add a `deploy` block. Exactly one agent in the score should declare it: that's the deploy entrypoint.

```ts title="tutti.score.ts"
import { defineScore, AnthropicProvider } from "@tuttiai/core";
import { GitHubVoice } from "@tuttiai/github";

export default defineScore({
  provider: new AnthropicProvider(),
  agents: {
    api: {
      name: "api",
      model: "claude-sonnet-4-6",
      system_prompt: "You are a customer-facing API agent.",
      voices: [new GitHubVoice()],
      permissions: ["network"],
      deploy: {
        target: "fly",                              // optional: --target wins
        region: "auto",
        scale: { min: 0, max: 3, memory: "512MB" },
        health: { path: "/health", interval_seconds: 30 },
        env: { LOG_LEVEL: "info" },                  // plaintext config
        secrets: ["ANTHROPIC_API_KEY", "GITHUB_TOKEN"], // names of required env vars
      },
    },
  },
});
```

The `secrets` array names every env var the runtime needs: the deploy bundler emits a matching `.env.deploy.example` next to your score so missing-vars are obvious before the platform rejects them.

## Step 2: Pre-flight check

```bash
tutti-ai deploy --target railway --dry-run
```

The dry run prints the deploy plan without invoking the platform CLI. Two static analyses run before any I/O:

1. **`scanForSecrets()`** walks your score and every imported package's entry file for `process.env.X` reads. It filters Node built-ins (`PATH`, `HOME`, `NODE_ENV`, etc.) and emits errors for undeclared required vars. If your code reads `process.env.STRIPE_SECRET_KEY` but `deploy.secrets` doesn't list it, the deploy fails fast with a clear message.

2. **`validateSecrets()`** warns on secret-shaped names (`*_KEY`, `*_TOKEN`, `*_SECRET`) sitting in plaintext `deploy.env`. Plaintext API keys block the deploy fail-fast: the platform's secret store is the right place for them, not your score file.

If the dry-run is green, drop `--dry-run` to deploy for real.

## Step 3: Deploy

```bash
tutti-ai deploy --target railway     # bundle + railway up
```

Tutti generates the bundle in `./tutti-deploy/`, writes `.env.deploy.example`, and dispatches to the platform CLI. On success it prints the deploy URL; on failure it surfaces the platform's error and exits non-zero.

### Targets

| Target | Generated files | Platform command dispatched |
| --- | --- | --- |
| `docker` | `Dockerfile`, `.dockerignore`, `docker-compose.yml`, `deploy.sh` | `docker compose build && docker compose up -d` |
| `railway` | All Docker files + `railway.json` | `railway up` |
| `fly` | All Docker files + `fly.toml` | `fly deploy` |
| `modal` | `modal_app.py`, `tutti.score.ts`, `.env.modal.example`, `deploy.sh` | `modal deploy modal_app.py` |
| `daytona` | `.devcontainer/devcontainer.json`, `.daytona/snapshots.yaml`, `.gitignore`, `daytona.sh` | `daytona create --no-ide` |

The Docker bundle runs as non-root user `tutti` (uid 1001), exposes port 3000 (configurable), and includes a healthcheck against the `health.path` you set. `NODE_OPTIONS --max-old-space-size` is computed from `scale.memory` so the runtime won't OOM under platform-imposed memory caps.

### Modal (scale-to-zero)

`tutti-ai deploy --target modal` runs the Tutti Node server inside `node:20-bookworm-slim`: Debian's apt `nodejs` is Node 18 and too old. The generated `modal_app.py` installs `tutti-ai@latest` + `@tuttiai/cli@latest` (pinnable via the `CLI_VERSION` constant before `modal deploy`), declares each `manifest.secrets` entry as `modal.Secret.from_name("tutti-<lowercase>")`, surfaces `manifest.env` as the function's `env=` dict, and exposes the server via `@modal.web_server(port=3000, startup_timeout=120)`. `manifest.scale.memory` (`"512mb"` / `"2gb"`) is converted to the integer Modal expects on `memory=`, defaulting to 2048.

Because Modal redeploys are functions, not slot-based releases, `tutti-ai deploy rollback` is reported as not applicable. `deploy status` dispatches to `modal app list`; `deploy logs` to `modal app logs <name>`.

Modal is a **serverless** target: between invocations the function hibernates. Anything held in-process memory (a non-persistent session store, a setInterval, a long-lived voice client cache) silently evaporates. Run [`tutti-ai deploy verify-hibernate`](/cli/reference#tutti-ai-deploy-verify-hibernate) on your score first; it checks for stores and timers that wouldn't survive the next cold start.

### Daytona (always-warm dev environment)

The Daytona bundle stands up a persistent dev environment from `mcr.microsoft.com/devcontainers/typescript-node:22`, installs `tutti-ai` via `postCreateCommand`, and forwards port 3000. After `daytona create` finishes, `daytona.sh` SSHes in and starts `tutti-ai serve`. The emitted `.daytona/snapshots.yaml` requests idle-hibernation (5 min) and auto-resume: its field names are not yet verified against the current Daytona schema, so the file ships with a TODO banner; treat hibernation as best-effort until that's confirmed.

### Cloudflare Workers (recognised, not yet wired up)

`DeployTarget` includes `"cloudflare"` so a score can declare it ahead of time, but no bundler ships in v0.26. The CLI errors loudly with *cloudflare deployment is not yet wired up in the CLI. Pass `--target docker|railway|fly|modal|daytona` to override.* rather than half-deploying.

### Conditional services

The bundler reads your score's `memory.provider` and per-agent `durable.store` to decide whether to add `postgres` or `redis` services:

- `memory.provider: "postgres"` → adds a postgres service to `docker-compose.yml`, sets `DATABASE_URL` in env.
- `durable.store: "redis"` → adds a redis service, sets `TUTTI_REDIS_URL`.

You can override either by setting the env var explicitly in `deploy.env` or by attaching a managed equivalent on the platform side.

## Step 4: Operate

Once shipped, the same CLI manages day-to-day operations:

```bash
tutti-ai deploy status              # platform-equivalent status check
tutti-ai deploy logs --tail         # follow logs
tutti-ai deploy rollback            # roll back to the previous release
```

Each subcommand dispatches to the matching platform command (`fly status`, `railway logs`, etc.) so you don't need to remember the platform's exact verbs.

## Pending approvals and restarts

The server image (`packages/server`, `dist/start.js`) keeps pending approvals, and the turn each paused run stopped at, so approving after a restart resumes the run from that point:

| Configuration | Where approvals live | Survive a restart |
|---|---|---|
| `TUTTI_PG_URL` set | Postgres (`PostgresInterruptStore`, `PostgresCheckpointStore`) | yes |
| otherwise `TUTTI_STATE_DIR` set and writable | `<dir>/interrupts/<id>.json` and `<dir>/checkpoints/<session>/<turn>.json` | yes |
| neither | memory, with a warning at start | no |

- Mount a persistent volume at the state directory (for example `-v tutti-state:/state -e TUTTI_STATE_DIR=/state`) for approvals and sessions to survive a container restart.
- Run one server per approval store: a file store or a Postgres table shared by two servers would let both resume the same run.
- Postgres that cannot be reached is not a reason to fall back to memory: the error surfaces on the first approval.
- Postgres checkpoints expire after their TTL (24 hours by default). An approval resolved after that is recorded, but its run cannot resume, and a warning says so.
- `tutti-ai serve` keeps approvals in Postgres when `TUTTI_PG_URL` is set and in memory otherwise; it does not read `TUTTI_STATE_DIR`.

After a restart the original `/run/stream` client is gone, so the resumed run's answer is on `GET /sessions/:id` rather than on that stream.

## Cost monitoring after deploy

Once your service is running, configure a `RunCostStore` so the cost-analysis CLI can read live data:

```ts
import { TuttiRuntime, PostgresRunCostStore } from "@tuttiai/core";

const runtime = new TuttiRuntime(score, {
  runCostStore: new PostgresRunCostStore({
    connection_string: process.env.DATABASE_URL!,
  }),
});
```

Then from your laptop:

```bash
tutti-ai analyze costs --last 7d --url https://api.example.com
```

Top runs by cost, daily-spend sparkline, and burn-rate optimisation hints. See [the CLI reference](/cli/reference#tutti-ai-analyze-costs) for the full command surface.

## Data residency

When you self-host, Tutti keeps sessions, approvals, memory and traces in the stores you configure, on the hosts where you run them. The framework has no hosted store of its own. What does leave the host, model calls first, is listed under [What leaves the host](#what-leaves-the-host). `deploy.region` picks the platform region the bundle runs in, and so where a store inside the container, or a Postgres or Redis service the bundler adds beside it, keeps its data (see [Conditional services](#conditional-services)). A managed database you attach instead keeps its data wherever you created it.

### Where each store keeps its data

| Data | Store (package) | What chooses where it goes | Default |
|---|---|---|---|
| Sessions | `InMemorySessionStore`, `FileSessionStore`, `PostgresSessionStore` (`@tuttiai/core`, table `tutti_sessions`) | `sessionStore` runtime option; score `memory: { provider: "postgres" }` with `memory.url`, else `DATABASE_URL`; server image: `TUTTI_STATE_DIR` | process memory (1,000 sessions, 24 hours idle), lost on restart |
| Approvals | `MemoryInterruptStore`, `PostgresInterruptStore` (`@tuttiai/core`, table `tutti_interrupts`), file store (`@tuttiai/server`) | `interruptStore` runtime option; server image: `TUTTI_PG_URL`, else `TUTTI_STATE_DIR` | none until you pass one; server image: memory, with a warning |
| Checkpoints | `MemoryCheckpointStore`, `PostgresCheckpointStore` (table `tutti_checkpoints`), `RedisCheckpointStore` (`@tuttiai/core`), file store (`@tuttiai/server`) | `checkpointStore` runtime option, or agent `durable.store` (`"postgres"` reads `TUTTI_PG_URL`, `"redis"` reads `TUTTI_REDIS_URL`); server image: as approvals | none until configured |
| Semantic memory | `InMemorySemanticStore` (`@tuttiai/core`) | agent `memory.semantic.store` takes your own `SemanticMemoryStore` | process memory; no other backend ships |
| User memory | `MemoryUserMemoryStore`, `PostgresUserMemoryStore` (`@tuttiai/core`) | agent `memory.user_memory.store`: `"memory"` or `"postgres"` (reads `TUTTI_PG_URL`) | off until configured |
| User model | `InMemoryUserModelStore`, `PostgresUserModelStore` (`@tuttiai/core`, table `tutti_user_profiles`) | `runtime.setUserModelStore(agent, store)`; Postgres takes `connection_string` | process memory |
| Schedules | `MemoryScheduleStore`, `PostgresScheduleStore` (`@tuttiai/core`, table `tutti_schedules`) | the store you pass to `SchedulerEngine`; Postgres takes `connection_string` | the store you pass |
| Run costs | `InMemoryRunCostStore` (`@tuttiai/telemetry`), `PostgresRunCostStore` (`@tuttiai/core`, table `tutti_run_costs`) | `runCostStore` runtime option; Postgres takes `connection_string` | not recorded until configured |
| Tool result cache | `InMemoryToolCache` (`@tuttiai/core`) | agent `cache` settings | process memory only |
| Skills | `InMemorySkillStore` (`@tuttiai/skills`) | `skillStore` runtime option | process memory |
| Inbox identities | `InMemoryIdentityStore` (`@tuttiai/inbox`) | `identityStore` inbox option | process memory |
| RAG chunks | `MemoryVectorStore`, `PgVectorStore` (`@tuttiai/rag`) | voice `storage.provider`: `"memory"` or `"pgvector"` with `connection_string`, else `RAG_PG_URL` | as configured on the voice |
| Traces (OpenTelemetry) | `initTelemetry` (`@tuttiai/core`), OTLP over HTTP | score `telemetry`: `enabled`, `endpoint`, `headers` | off; when enabled without `endpoint`, `http://localhost:4318` |
| Spans | `OTLPExporter`, `JsonFileExporter` (`@tuttiai/telemetry`) | `TUTTI_OTLP_ENDPOINT` or `TUTTI_TRACE_FILE` | no exporter installed |
| Logs | pino logger (`@tuttiai/core`) | `TUTTI_LOG_LEVEL` | the process's standard output |
| Claude Code provider state | `claude-code-sessions.json` and `claude/` under `TUTTI_STATE_DIR` (server image) | `TUTTI_STATE_DIR`, `CLAUDE_CONFIG_DIR` | the CLI's own config directory, `~/.claude` |

The server image's files under `TUTTI_STATE_DIR`, and what survives a restart, are set out in [Pending approvals and restarts](#pending-approvals-and-restarts). Sessions read `memory.url` or `DATABASE_URL`, while approvals, checkpoints, user memory and the server image read `TUTTI_PG_URL`.

### What leaves the host

- **Model calls.** The prompts, tool results and replies of a run go to the model provider you configure, and are processed wherever that provider serves them. `AnthropicProvider` and `GeminiProvider` call the provider's own API and take no endpoint or region option. `OpenAIProvider` takes `base_url`, so it can point at a proxy or a compatible server you run. `OpenRouterProvider` takes `base_url`, `route` and `models`, and OpenRouter picks the upstream provider. A `SmartProvider` from `@tuttiai/router` may send a call to any provider it wraps. See [Providers](/guides/providers/).
- **Claude Code.** With `ClaudeCodeProvider`, the Claude Code CLI makes the model calls itself, under its own login and configuration.
- **Realtime.** `@tuttiai/realtime` streams the conversation to the OpenAI Realtime API.
- **Voices.** A voice sends what the agent hands it to the service it wraps, such as GitHub, Slack or Stripe. The RAG voice sends text to the embedding provider you configure (OpenAI, Voyage AI, or a local server at `base_url`), and the Knowledge voice calls the `url` you set.
- **Trace exporters.** Spans and traces go only to the endpoint or file you configure.
- **Registry lookups.** `tutti-ai search` downloads the voice registry from GitHub (`tuttiai/voices`). It is a CLI command, not part of the runtime, and it sends no run data.

### Limits

AWS, GCP and Azure deploy targets and multi-region deployments are not supported yet; see [What's not yet shipped](#whats-not-yet-shipped).

## What's not yet shipped

- **Cloudflare Workers bundler.** The target value is recognised but the bundler is a follow-up. Until then, the CLI rejects `--target cloudflare` with a clear error.
- **AWS / GCP / Azure**: not yet. The bundler is structured around platforms with a single deploy verb; the cloud providers need an opinion about ECS vs Lambda vs Fargate, GKE vs Cloud Run, etc., that we haven't picked yet. For now use the Docker bundle and ship via your existing infra-as-code.
- **Multi-region**: `region: "auto"` picks one region. Multi-region active-active is platform-specific (Fly supports it natively, others don't) and not abstracted yet.
- **Blue/green**: rollback is single-step, not slot-based. We rely on the platform's release history rather than maintaining two deployments.
- **Modal rollback**: Modal redeploys are functions, not slot-based releases; `tutti-ai deploy rollback` reports as not applicable on Modal.
